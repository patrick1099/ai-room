# ai-room 双 AI 顾问房间设计

日期：2026-07-23  
状态：已确认并完成自审，待用户书面复核

## 1. 背景与目标

用户会同时打开 Claude Code 和 Codex 两个交互式会话。需求澄清完成后，当前负责与用户交流的
AI 继续承担代码实现、运行、编译和测试；当它需要技术决策、文档审查或上下文压缩时机判断时，
应自行把任务交给另一个 AI。用户不需要理解技术问题，也不需要在两个窗口之间复制粘贴。

两个工具地位对等：谁当前服务用户，谁就是主聊 AI；另一边临时成为顾问。下一次角色可以互换。

## 2. 已选择方案

采用原生 Windows Python 小工具，通过本地 SQLite 房间传递消息。两个交互式 AI 会话分别调用
阻塞式 `wait` 命令；收到消息时命令输出任务并结束，从而唤醒所在会话的 AI。系统不启动守护
进程，不通过网络通信，也不自动启动新的 Claude Code 或 Codex 会话。

未采用以下方案：

- `agmsg`：已有跨 AI 消息能力，但 Windows 依赖 Git Bash 和外部 `sqlite3`，Codex 实时监听仍有
  额外桥接层，而且无法直接表达本项目的文档写入边界。
- MCP Agent Mail：邮箱、搜索、文件租约和服务端能力完整，但对两个本地交互式会话过重。
- 按需启动非交互式 CLI：无法保留用户希望看到的两个常驻交互式窗口。

## 3. 用户交互

1. 用户分别打开 Claude Code 和 Codex，并在同一工作目录执行 `ai-room join <agent>`。
2. 两边执行 `ai-room wait`，Shell 阻塞等待，不持续输出。
3. 用户要与某一边说话时，按 `Esc`；若客户端未映射该键，则按 `Ctrl+C`。
4. 用户正常提出需求，主聊 AI 执行实际工作。
5. 主聊 AI 需要顾问时执行 `send`，然后进入 `wait`。
6. 顾问的 `wait` 返回任务。顾问完成允许的决策或文档修改，执行 `reply` 后再次进入 `wait`。
7. 主聊 AI 被回复唤醒，继续工作，完成后也重新进入 `wait`。

中断 `wait` 只结束当前 Shell 调用，不退出房间，不确认消息，也不清除任务。

## 4. 房间与本地数据

运行数据位于 `%LOCALAPPDATA%/ai-room/`，不写进项目仓库。每个工作目录对应一个独立房间：

- 房间键使用规范化后的 `git rev-parse --show-toplevel` 结果；非 Git 目录使用规范化绝对路径。
- 不使用 `git common-dir` 作为房间键，因此同一仓库的不同 worktree 默认互相隔离。
- 用户可以显式指定房间名，但显式名称仍绑定首次登记的工作目录，防止误接到另一个目录。

SQLite 开启 WAL，`busy_timeout` 固定为 5 秒。数据库只保存房间、成员、消息、任务、确认状态、等待心跳、
上下文采样和文件基线元数据。正文不复制整个项目或完整会话 transcript。

## 5. 组件边界

### 5.1 命令入口

提供六项第一版能力：

- `join codex|claude`：登记当前交互式会话、工作目录和会话记录定位信息。
- `wait`：采集自身上下文，必要时发起压缩检查，然后阻塞等待下一条消息。
- `send`：创建技术决策、文档审查、计划审查或压缩检查任务。
- `reply`：验证任务结果和文件边界，原子地回复并关闭当前任务。
- `status`：显示成员是否已加入、是否正在等待、当前任务和排队消息。
- `leave`：清理成员的在线/等待状态，不删除历史消息。

### 5.2 消息存储

消息层只负责可靠传递、排序、去重和状态转换，不决定 AI 应该如何回答。写入使用短事务；读取
允许并发；一个房间同一时间只有一个顾问任务处于 `working`，后发任务保持 `queued`。

### 5.3 会话适配器

- Codex 适配器读取 Shell 暴露的 `CODEX_THREAD_ID`，定位对应 session JSONL，并使用最近一次
  `token_count.info.last_token_usage.input_tokens` 作为当前上下文输入量。
- Claude Code 通过一个最小会话登记 hook 保存 `session_id` 和 `transcript_path`。适配器读取最近
  一条 assistant usage，按当前格式计算
  `input_tokens + cache_read_input_tokens + cache_creation_input_tokens`。
- 所有格式解析集中在适配器中，并用脱敏 fixture 固定当前格式。读取失败返回 `unknown`，不得用
  文件大小或累计总 token 冒充当前上下文长度。

### 5.4 文件边界验证器

每个可修改文档必须由主聊 AI 以规范化的精确路径列入 `writable_docs`。目录、扩展名和模糊匹配
不能自动扩大权限。允许新建文档时，也必须预先给出其精确目标路径。

任务开始时记录工作区文件基线。Git 仓库覆盖全部 tracked 文件和
`git ls-files --others --exclude-standard` 返回的非忽略 untracked 文件；非 Git 目录覆盖除工具自身
运行目录外的全部普通文件。每个纳入范围的文件记录内容哈希，任务回复前对同一范围再次采样：

- 允许清单内的变化可以提交给主聊 AI；
- 清单外出现新变化时，`reply` 失败并列出路径；
- 基线之前已经存在的未提交变化只要内容未继续改变，就不算顾问越界；
- 工具绝不自动恢复、覆盖或删除越界文件。

第一版的强制保障发生在任务完成闸门。平台侧的动态工具调用拦截可作为以后增强，不是第一版
可信性的前提。

## 6. 消息与任务契约

顾问请求至少包含：

- 唯一消息 ID、房间 ID、发送方、接收方和创建时间；
- 类型：`decision`、`requirements_review`、`design_review`、`plan_review`、`context_check`；
- 问题正文、相关文档、精确可写文档清单；
- 发送方当前上下文 token、上下文窗口大小和采样来源；
- 工作节点记录文档及下一步入口；
- `reply_to` 和幂等键。

顾问任务只有三种终态：

- `DONE`：决定已给出，或允许文档已经修改完成；
- `BLOCKED`：存在需求矛盾、必须由用户选择，或缺少无法取得的信息；
- `COMPACT_READY`：达到阈值且已确认处于安全压缩节点。

不存在“请对方再完整审一遍”的终态。`DONE` 后任务关闭；新任务必须有新的问题和 ID。

## 7. 上下文压缩管家

每次进入 `wait` 时采集当前 AI 的上下文长度：

- 小于 150k：直接等待，不发提醒。
- 150k 到 200k：若本轮尚未检查，则自动向另一边创建 `context_check`。
- 大于 200k：不在操作中途强压；要求先结束当前最小工作单元、记录现场，再优先检查。

顾问不能只看 token 数。它必须确认：

1. 当前小任务已完成或明确暂停；
2. 重要决定、已做改动、验证结果和未解决问题已写入工作文档；
3. 下一步入口明确，新上下文能仅凭这些记录继续；
4. 没有需要保留在当前对话中才能安全完成的进行中操作。

条件满足时返回 `COMPACT_READY`，包含工具名、token 数、记录文档和压缩后的恢复入口。主聊 AI
用大白话提醒用户手动执行 `/compact`。工具永不代用户执行压缩。

条件不满足时返回 `CHECKPOINT_NEEDED` 作为非终态回复，列出缺失记录。主聊 AI 补齐后通过
`wait --checkpoint <exact-path>...` 重新触发检查。为避免重复提醒，同一会话在当前输入 token 相对
上次检查增长不足 10k 且 checkpoint 精确路径集合与内容哈希均未变化时，不重复创建相同检查。

压缩后，适配器观察到当前上下文下降，自动清除待压缩状态；房间成员身份和未完成消息不受影响。

## 8. 并发、取消与恢复

- `wait` 只读取待处理消息，不在输出前永久确认；正式 `reply` 或显式确认后才推进游标。
- `Esc`、`Ctrl+C`、进程崩溃或断电后，未确认消息仍会再次投递。
- 消息 ID 和幂等键防止重复回复；重复执行同一 `reply` 返回已有结果，不创建第二份回复。
- 同时产生的任务按数据库序号排序。一个任务处理中时，其他任务保持排队，不造成交叉等待。
- `wait` 每 5 秒更新一次心跳并每 500 毫秒检查一次消息；心跳超过 15 秒未更新即视为未在等待。
  `join` 只表示成员已登记，不能冒充当前正在等待。
- 发送前若对方从未加入，明确报错；对方已加入但未等待时允许排队，并在状态中说明。

## 9. 错误处理

- SQLite 短暂锁定：在限定时间内重试；超过 `busy_timeout` 后显示可操作错误。
- 数据库无法打开或 schema 不兼容：停止写入，不自动重建或删除旧库。
- 消息格式损坏：隔离该消息并显示 ID；后续正常消息仍可读取。
- 顾问越界修改：拒绝 `reply`，列出路径，不自动回滚。
- 允许文档不存在：仅当精确路径已在 `writable_docs` 中时允许新建。
- token 读取失败：记录 `unknown`，跳过自动压缩判断，正常消息功能继续可用。
- 对方离线：消息保留；`status` 明确区分“未加入、已加入未等待、正在等待”。

## 10. 验证策略

### 10.1 自动测试

- 两个模拟 AI 完成 `join -> wait -> send -> reply -> wait`。
- 取消、进程终止和重启后未处理消息仍存在。
- 重复读取和重复回复保持幂等。
- 同时发送按序处理且不死锁。
- 不同仓库和不同 worktree 不串房间。
- 中文消息、中文路径和 Windows 路径正常往返。
- 允许清单、路径规范化、新建文档和越界修改检查正确。
- 原有 dirty worktree 修改不被覆盖，也不被误算为顾问新改动。
- Codex、Claude 两种脱敏会话 fixture 能提取当前上下文；缺失和格式变化返回 `unknown`。
- 149k、150k、200k 及 200k 以上的边界行为正确。
- 达到 token 阈值但 checkpoint 不完整时不返回 `COMPACT_READY`。
- SQLite 占用、损坏消息和 schema 不兼容给出明确错误。

### 10.2 真实双窗口验收

1. 打开 Claude Code 和 Codex，加入同一房间并等待。
2. 手动中断一边，发起技术决策和文档修改请求。
3. 确认另一边被唤醒，只修改允许文档，并能回复唤醒主聊 AI。
4. 中断并重启其中一边，确认消息继续投递。
5. 使用脱敏的高 token fixture 走通压缩提醒，不真实消耗 150k token。

## 11. 第一版不做

- 顾问修改源代码、运行测试、编译、部署或操作真实系统。
- 两个 AI 自由聊天、多人团队、任务看板或通用 agent 编排。
- 自动执行 `/compact`。
- 跨设备、网络服务器、Web UI 或远程同步。
- 自动回滚越界文件。
- 支持 Claude Code 和 Codex 之外的第三个 AI 工具。

## 12. 完成标准

第一版只有在自动测试通过，并由用户在真实 Claude Code/Codex 双窗口中完成第 10.2 节验收后，
才可以宣称可用。仅有代码、单元测试或单边 CLI 演示不能算完成。
